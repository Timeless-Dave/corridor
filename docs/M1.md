M1 is complete. All 12 tests passed, including remote integration validation, and the

## Remote setup

1. Create a FalkorDB instance at https://app.falkordb.cloud/.
2. Obtain its host, port, username, password, and TLS requirement from its connection settings.
3. At the repository root, copy `.env.example` to `.env` and enter those values locally.
   Keep `GRAPH_NAME=corridor`. Do not commit or paste the password into chat.
4. TLS: **FalkorDB Free** has no TLS — set `FALKORDB_TLS=false` and turn off TLS in
   FalkorDB Browser. Paid tiers with TLS enabled use `FALKORDB_TLS=true`; certificate and
   hostname verification are enabled; use the exact supplied hostname. `.env.example`
   defaults to `true` for generic cloud endpoints.
5. Copy **host and port** from the instance **Connectivity** tab while status is
   **Running** (not only from an old Browser screen). Quick check:
   `dig +short "$FALKORDB_HOST"` should return real A/AAAA records, not
   `sinkhole.paloaltonetworks.com`; `nc -vz host port` should succeed before live tests.

The official `falkordb` Python client is the only database client. Connection and query
errors never include exception payloads or connection credentials. Connection timeout
is 10 seconds and socket timeout is 30 seconds.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r api/requirements.lock.txt
cd api
../.venv/bin/python -m data.generate --seed 42
../.venv/bin/python -m unittest discover -s tests -v
CORRIDOR_LIVE_TESTS=1 ../.venv/bin/python -m unittest tests.test_live -v
../.venv/bin/python -m data.load
../.venv/bin/python -m data.verify
```

The integration test creates a unique `corridor_test_<uuid>` graph, checks counts,
all four proofs, benign controls, owner routing, current precedent, historical memory,
indexes, occupied-graph refusal, and reset/reload, then deletes only its test graph.
The connection user must be permitted to list/create/delete graphs.

The loader refuses an occupied graph. To deliberately replace the configured demo graph:

```bash
../.venv/bin/python -m data.load --reset
```

Loads use batches of 500, with all nodes before relationships. This is a single-user
bootstrap operation, not an atomic migration: a failed load may leave partial data.
Fix the error and explicitly reset before retrying. Never run simultaneous loaders.
Generation is deterministic for seed 42; it uses a fixed timestamp, synthetic names,
and non-dialable synthetic phone identifiers. It does not need an LLM or API key.

## Local alternative

At the repository root, run `docker compose up -d`. Use host `localhost`, port `6379`,
blank username/password, and `FALKORDB_TLS=false` in `.env`. Browser is at
http://localhost:3000. Docker is not installed in the current workspace environment.
The Compose image follows the official `latest` development image; record its resolved
digest and server version when live validation is performed.

## Browser walkthrough

Open your instance's FalkorDB Browser and select the `corridor` graph. Open each query
file below and paste its entire contents into the query editor. Prepend the corresponding
`CYPHER` parameter header on a separate line (this supplies values without changing the
query). Run in table view to inspect returned IDs, amounts, and timestamps.

| Query in `api/queries/` | Parameter header | Expected evidence |
|---|---|---|
| `proof_cycle.cypher` | `CYPHER account_id='cycle_0'` | `cycle_0` through `cycle_4`, returning to `cycle_0`; amounts 480, 475, 470, 465, 460; increasing timestamps spanning 4 hours |
| `proof_fan_in.cypher` | `CYPHER account_id='collector_0' since=1792065599 until=1792238400 max_amount=500.0` | 12 distinct senders, total 4866 USD, 11-hour span |
| `proof_shared.cypher` | `CYPHER account_id='cycle_0'` | 9 accounts, 4 owners, 2 devices, 3 phones |
| `proof_ajo.cypher` | `CYPHER pool_id='pool_abuse'` | `ajo_0` receives in rounds 0→1 and 1→2; four contributors share `ajo_device` |

Ground-truth IDs and exact parameters are in `api/data/ground_truth.json`.
The shared-identifier proof establishes shared infrastructure, not fraud. Run it with
`account_id='acct_0000'` to see a benign two-account family. Run the ajo proof with
`pool_id='pool_00'` to see no repeated-recipient/device evidence for a legitimate pool.

For a visual view, paste `browser_neighborhood.cypher` and prepend one of:
`CYPHER account_id='cycle_0'`, `CYPHER account_id='collector_0'`, or
`CYPHER account_id='ajo_0'`. Switch to graph view. This returns real graph paths,
whereas the four proofs return compact tabular evidence. Use `browser_pool.cypher`
with `CYPHER pool_id='pool_abuse'` to view pool memberships and payout edges.

Before M3, manually run and explain every query: its start node, traversal, filters,
and returned evidence. M2 will validate algorithms and shortest-path syntax.

## Verification record

**12 tests passed, zero skipped**, including the live remote integration test
(44.904 seconds for the full suite). The configured demo graph contains **8,121 nodes
and 26,659 relationships**. All four proofs and both benign controls passed again
against the demo graph after loading. The graph module reports version `42200` (4.22.0).

The live test verified label/relationship counts, all six indexes, corridor ownership,
current precedent selection, seeded history, refusal to overwrite a populated graph,
and reset/reload reproducibility. Its disposable graph and this session's diagnostic
graph were deleted. A partial test graph from the earlier connectivity failure may
still remain; it was not deleted without identifying it conclusively.

The cycle proof uses five explicit directed edge aliases. On this server the original
variable-length closed path returned unexpected node/timestamp ordering. The revised
proof checks distinct accounts, chronological transfers, decreasing amounts, and the
72-hour bound directly. Verification also asserts the exact ordered IDs, amounts, and
timestamps. M2 must independently validate its generic variable-length traversal.

Browser visualization queries returned 24 rows for `cycle_0`, 27 for `collector_0`,
83 for `ajo_0`, and 13 for `pool_abuse`. These queries were executed through the official
client; manual inspection in Browser remains your review checkpoint before M3.
Synthetic evidence and verification metadata are saved in
[m1-verification.json](m1-verification.json).

Automatic client retries are disabled to avoid repeating non-idempotent writes after
an uncertain response. Test cleanup preserves the original failure and suppresses
raw connection errors.
